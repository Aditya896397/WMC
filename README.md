# 5G-Based Smart Ambulance Communication System
### Patient Monitoring · Mobility-Aware Network Handover · Hospital Coordination — *software simulation*

A complete, interactive **software simulation** for a Wireless & Mobile Communication project. A virtual
ambulance drives a real Chennai road route. Virtual patient sensors send synthetic vital signs over a simulated
**BLE** link to an **ambulance gateway**. The gateway forwards packets to the hospital over a simulated **5G NR /
4G LTE** network that has path loss, cell selection, **handover**, **5G→4G fallback**, **OFFLINE buffering** and
recovery. A **FastAPI** backend owns the single shared simulation and streams it over **WebSockets** to a
**Streamlit** dashboard.

> ⚠️ **Important disclaimers**
> - All data is **synthetic**. No physical sensors, ESP32, Raspberry Pi or 5G modem are used.
> - Vital signs are generated by stochastic models. They are **not real medical measurements**, and alerts are
>   **demonstration alerts, not clinically validated diagnoses**.
> - Network figures come from a **simplified educational model**. It is **not** a standards-compliant 3GPP
>   simulation, and the figures are **not real-world 5G measurements**.

## 1. Architecture

```
VIRTUAL PATIENT SENSORS (HR/SpO2 oximeter, temperature patch, ECG patch)
        │  synthetic readings (Ornstein–Uhlenbeck processes, 3 scenarios)
        ▼
BLE COMMUNICATION SIMULATOR   — RSSI, per-attempt loss, link-layer retries, latency
        ▼
AMBULANCE GATEWAY             — timestamp, packet ID, validation, forward / buffer queue
        │  + GPS from the AMBULANCE MOVEMENT SIMULATOR (OSRM route / fallback)
        ▼
5G NR / 4G LTE NETWORK SIMULATOR — path loss, shadowing, cell selection, A3 handover,
        │                          fallback, OFFLINE mode, HARQ, latency, throughput
        ▼
FASTAPI BACKEND (single shared SimulationEngine + async tick loop)
        ├── SQLite (SQLAlchemy) — vitals, locations, packets, handovers, events, alerts, experiments
        └── WebSocket /ws/live — snapshot broadcast every tick
        ▼
STREAMLIT DASHBOARD (8 pages) ──► HOSPITAL MONITORING CENTRE
```

Key design rules (all implemented):
* **One simulation instance.** The FastAPI process creates exactly one `SimulationEngine`
  (`backend/services/runtime.py`) and advances it in a background asyncio task. Streamlit never simulates
  anything. It only reads snapshots and sends control commands.
* **All changing values come from the engine.** Nothing in the UI is hard-coded or randomly generated.
* **Synchronised sub-simulators.** Patient, BLE, GPS, network and gateway advance together in 0.5 s sub-steps of
  simulated time.
* **Non-blocking UI.** A background WebSocket client thread (`frontend/utils/live.py`) keeps the latest snapshot.
  Pages refresh with `st.fragment(run_every=…)` and fall back to REST if the WebSocket drops.

## 2. Setup

Requires **Python 3.10–3.12** (3.11 recommended; very new Python versions may lack binary wheels).

```bash
cd smart_ambulance
python -m venv .venv
# Windows:  .venv\Scripts\activate        macOS/Linux:  source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env        # (cp on macOS/Linux) — optional
python -m backend.database.init_db   # optional: tables are also created automatically at backend start
```

### Deploy on Streamlit Community Cloud
1. Go to **share.streamlit.io** → **Create app** → pick this GitHub repo and branch `main`.
2. **Main file path:** `frontend/app.py`
3. **Advanced settings → Python version:** 3.11 or 3.12.
4. Deploy. No secrets are needed.

Streamlit Cloud runs only the Streamlit process, so when no backend answers at `BACKEND_URL`, the dashboard
**starts the FastAPI backend inside the same process** (`frontend/utils/embedded.py`). Everything (REST,
WebSocket `/ws/live`, SQLite) works the same, but on localhost inside the container, so the Swagger UI is not
public. Note that the cloud's SQLite file resets whenever the app restarts. To turn this off (when you run a
separate backend), set `EMBED_BACKEND=false`.

> Running locally with `streamlit run frontend/app.py` alone works the same way: the backend starts embedded.

### Demonstration script (≈ 5 minutes)
1. **Overview**: press **▶ Start**. The pipeline strip shows Sensors → BLE → Gateway → 5G/4G → Backend → Hospital.
2. **Ambulance Tracking**: watch the ambulance move across OpenStreetMap, with cell coverage circles and the
   dashed link to the serving cell.
3. **Mobile Comm Concepts**: walk through path loss, Doppler shift and the A3 handover rule with live values.
4. **5G/4G Network Simulator**: watch the BS1 → BS2 handover, the 5G→4G fallback in the coverage gap (BS3), and the
   return to 5G (BS4). Toasts show `HANDOVER INITIATED: BS1 → BS2` and `HANDOVER COMPLETED: BS2`.
5. Click **Simulate network failure**. The status goes **OFFLINE** and the buffered packet count climbs. Click
   **Restore connectivity**. The backlog flushes and a recovery record appears with outage duration, buffered
   count and recovery time.
6. **Patient Monitoring**: switch to **Scenario B** or **C** and watch the demonstration alerts fire.
7. **Hospital Monitoring**: send a doctor → ambulance message. It is delivered with the current network latency,
   or queued while OFFLINE.
8. **Network Performance Analysis**: run an experiment that compares **A. 5G-only**, **B. 4G-only** and
   **C. 5G+4G fallback+buffering**. Results are saved to SQLite.

Tip: on the **Simulation Controls** page, increase *time acceleration* to drive the route faster.

## 5. Network simulation model (Module 5)

| Element | Model |
|---|---|
| Base stations | BS1 5G NR, BS2 5G NR, BS3 4G LTE (umbrella cell), BS4 5G NR. Each has ID, type, coordinates, coverage radius, Tx power, frequency, bandwidth, enabled flag |
| Path loss | `PL(d) = 20·log10(4πf/c) + 10·n·log10(d)` (log-distance from 1 m). Defaults n = 3.8 (5G, 3.5 GHz) and 3.4 (4G, 1.8 GHz) |
| Shadowing | Log-normal, σ = 4 dB, spatially correlated over 50 m (Gudmundson AR(1)) |
| Signal strength | `S = Ptx + G_ant − PL + X_σ − Δ_5G(degradation)` in dBm (an RSRP-like indicator) |
| SINR | `S − noise floor` (−110 dBm; interference is folded into the floor) |
| Throughput | `0.6 · B · min(log2(1+SINR), SE_max)` with SE_max = 7.4 (5G) / 5.5 (4G) b/s/Hz |
| Block errors | `BLER = 1/(1+e^{1.1(SINR−1)})`, up to 4 HARQ transmissions; residual failure = packet loss |
| Availability | enabled ∧ d ≤ radius ∧ S ≥ S_min (−105 dBm 5G / −112 dBm 4G) ∧ allowed by policy |
| Cell preference | score = S + 6 dB if 5G (HYBRID mode), so 5G is preferred when suitable |
| Handover | A3-like: neighbour score > serving + hysteresis (3 dB) for TTT (1.5 s), and neighbour S ≥ S_min + 4 dB margin. Immediate handover if the serving cell becomes unusable (radio-link failure or policy fallback). OFFLINE if no cell is available |
| Interruption | intra-NR 30±8 ms, NR→LTE 90±20, LTE→NR 80±20, intra-LTE 45±10, +200±50 ms after RLF; re-attach after outage 120±30 ms |
| Latency | BLE + 1 ms gateway + air (4 / 15 ms) + core (6 / 18 ms) + backhaul 8 ms + serialisation × HARQ tx + HARQ RTT (1 / 8 ms) + exponential jitter + configured extra + buffer wait |
| Buffering | While OFFLINE or during handover execution, packets are queued in the gateway (capacity configurable) and flushed in order once the link is usable |

**Limitations:** no fast fading, no explicit inter-cell interference, no scheduling or load, no beamforming, no RRC
state machine or measurement gaps, illustrative base-station placement. The model is meant to explain the
**concepts** (coverage, handover, fallback, buffering), not to predict real network performance.

### Performance metrics (Module 9)
Every metric is computed from the **packet log** (generation and delivery timestamps, status) and the **event
log** (handovers, outages, connected time). See `backend/simulation/performance.py`. Experiments run the full route
three times with the **same seed** (common random numbers) and change only the network configuration.

## 7. Database

SQLite file: `database/smart_ambulance.db` (created automatically, persists across restarts, WAL mode).
Override it with `DATABASE_URL` (for example a Supabase Postgres URL; requires `pip install "psycopg[binary]"`).

| Table | Content |
|---|---|
| `patients`, `ambulances` | Seed reference data (P001, AMB001) |
| `base_stations` | Base-station configuration. UI edits are saved here and reloaded at startup |
| `simulation_runs` | One row per run (reset) with its configuration |
| `patient_vitals` | Every vitals packet (timestamped, per run) |
| `ambulance_locations` | GPS trace (1 sample per simulated second) |
| `packet_logs` | Every packet: status, latency, network, BS, buffered, HARQ, loss reason |
| `handover_logs`, `network_events` | Handover details and all network/system events |
| `emergency_alerts` | Demonstration alerts |
| `doctor_messages` | Doctor ↔ ambulance messages |
| `simulation_experiments` | A/B/C experiment results with parameters |

Initialise or seed manually: `python -m backend.database.init_db`. To start over, stop the backend and delete
`database/smart_ambulance.db`.

```
├── frontend/
│   ├── app.py                  # navigation, theme, sidebar
│   ├── views/1_Overview.py … 8_Simulation_Controls.py   # the 8 pages (see note below)
│   ├── components/             # theme, charts, map_view, layout
│   └── utils/                  # api.py (REST client), live.py (WebSocket feed)
├── database/                   # SQLite file lives here
├── tests/
└── .streamlit/config.toml      # dark navy theme
```

> **Why `views/` instead of `pages/`?** The dashboard uses `st.navigation` (grouped sidebar, shared theme,
> shared WebSocket feed). A folder literally named `pages/` next to `app.py` makes Streamlit fall back to its
> legacy auto-discovery when a page URL is opened directly, which bypasses `app.py`. Naming it `views/` avoids that.

## 10. Troubleshooting

* **"Backend offline" in the dashboard:** start Uvicorn first, and check that `BACKEND_URL` matches.
* **Map shows "FALLBACK" route:** the OSRM public server was unreachable. The predefined route is used
  automatically. Set `USE_OSRM=false` for fully offline demos.
* **Windows `DLL load failed … filename or extension is too long`:** the project or venv path exceeds
  Windows' 260-character limit. Move the project to a short path (e.g. `C:\projects\smart_ambulance`) or create
  the venv at a short path.
* **Port in use:** `uvicorn backend.main:app --port 8001` and set `BACKEND_URL=http://localhost:8001`.
